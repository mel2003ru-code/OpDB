# LAB-001 — честное сравнение OpDB Lens / Source / SQLite

**Статус:** черновой исследовательский эксперимент. Это не принятие M5 и не тест самостоятельной СУБД.

## Три режима

Для одной и той же группы и одинакового набора ключей/BLOB:

1. TruthStore(path, lens=True).group_stats("g1") — Lens.
2. TruthStore(path, lens=False).group_stats_source("g1") — прямой пересчёт Source.
3. sqlite3 + SQL COUNT и SUM(length(v)) — SQLite напрямую.

**Все три используют SQLite как хранилище.** Мы измеряем преимущества агрегата и накладные расходы слоя OpDB, а не сравниваем независимые СУБД.

## Воспроизведение

Из корня репозитория на Python 3.11+:

    python -m unittest discover -s tests -p 'test_*.py'
    python -m research.opdb_vs_sqlite --sizes 10000 100000 1000000 --seed 1729 --reads 100

Для небольшой проверки:

    python -m research.opdb_vs_sqlite --sizes 1000 --seed 1729 --reads 10

Скрипт печатает JSON Lines: фактический Git HEAD, seed, версии Python/SQLite, платформу и CPU; затем для каждого размера — контроль правильности, время заполнения, время открытия и построения Lens, median/p95/p99 агрегатных чтений, размер файлов базы/WAL после закрытия.

Генератор с фиксированным seed создаёт одинаковые ключи gN/XXXXXXXXX и BLOB, в том числе пустые. Запись происходит через публичный OpDB API, а независимая Python-модель и прямой SQL проверяют число строк и сумму байт. Любое расхождение прерывает эксперимент.

## Ограничения

- Холодное построение Lens и прогретые чтения измеряются отдельно; стоимость построения не должна исчезать при подсчёте общего TCO.
- Прямой SQLite не делает всех проверок типов и ограничений OpDB. Его время нельзя интерпретировать как выигрыш самостоятельного движка.
- p95/p99 из 100 замеров на одном CI раннере — лишь предварительная оценка, не SLA. Требуются повторные запуски на фиксированной машине.
- **Пока нет измерений** конкурентных транзакций, аварийного восстановления, реального SQLite I/O, RSS, стоимости поддержки Lens при записи и нативного хранилища. У TASK-007 отдельные бенчмарки записи.
- R01/R03: группа и индекс/Lens. R02/R08: предварительные размер файлов и задержки. R10: проверка результатов. R04/R05/R09 — пока модели, поскольку соответствующие механизмы OpDB не реализованы.
- Привилегированный внешний писатель остаётся за границей модели доверия; P0 Issue #21 не закрыт.
- После rerun старого Actions переменная GITHUB_SHA могла показывать старую версию, хотя checkout получил новый main. В LAB-001 читаем SHA прямо из git HEAD, не из переменной события.
