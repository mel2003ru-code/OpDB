## Синтетический benchmark — только SQLite

Условия: 5000 одинаковых детерминированных строк, 250 одинаковых действий на прогон (около 18% UPDATE; остальные селективные SELECT), одинаковые хеши входного trace и ответов, по 5 повторов без индекса и с индексом `(tenant,bucket)`. Порядок политик перемешивается по seed, стоимость `CREATE INDEX` и последующего обслуживания учитывается в сумме SQL-операций + DDL. Исключены первоначальное заполнение и последующая контрольная проверка; замеры преимущественно на тёплом файловом кэше.

| Показатель | SQLite без индекса | SQLite + заранее создаваемый индекс |
|---|---:|---:|
| Медиана суммарного SQL+DDL времени, мс | 46.9367 | 17.4469 |
| Медиана p99 по отдельным прогонам, мс | 0.5230 | 0.4407 |
| Медиана максимума задержки по прогонам, мс | 0.7311 | 0.5189 |
| Повторений | 5 | 5 |

Парное отношение суммарного времени `индекс / без индекса`: медиана **0.3680×**, диапазон **0.3350–0.5373×**. Это демонстрация контроля стоимости построения **в конкретной синтетической SQLite-нагрузке**, а не конкурентное превосходство OpDB. Не заявляем статистическую значимость за пределами стенда; 5 повторов недостаточно для внешнего performance claim. p99 в таблице — медиана индивидуальных p99, **не общий p99 всех 1250 действий**.

## Список блокирующих вопросов

1. **Q-001 — FAIL намеренно небезопасного Lens.** При внешней записи Lens возвращает устаревшее значение, хотя целостность SQLite исходника сохранена. Реальная Safety должна демонстрировать защиту/откат, не просто version epoch.
2. **Q-002 — NOT VERIFIED R12.** В чужом предыдущем протоколе сообщалось 0 вместо 8502 после DDL с кэшированным prepared expression. В новой лаборатории не воспроизведено, не атрибутировано SQLite. Нужен оригинальный testcase `hot/seed203` и проверки C API разных сборок.
3. **Q-003 — NOT VERIFIED реального OpDB Proof Gate.** Снимок, replay, proof, switch, откат, DDL, внешние процессы и bounds блокировок не исполнялись на target.
4. **Q-004 — NOT VERIFIED физическое I/O и power loss.** `os._exit` и `/proc/self/io` не равны отключению питания и телеметрии устройств.
5. **Q-005 — NOT VERIFIED PostgreSQL/MySQL и GitHub Actions.** Исполняемые адаптеры и workflow подготовлены, но серверы/CI-run отсутствовали.
6. **Q-006 — NOT VERIFIED обобщение на пользовательские трассы и производственную нагрузку.** Нет анонимизированного реального воспроизводимого workload, контролируемого оборудования и статистически достаточных серий.

## Следующий шаг для Safety / Core

Safety передаёт Proof Gate как доступный в disposable-режиме target с точками fault injection на фазах `snapshot → build → catch-up → verify → publish → serve → rollback`. Core передаёт query/transaction adapter и hash исполняемого build. Quality запускает свою матрицу, сохраняет все неправильные ответы с минимальными сценариями, не меняя ни один тест для прохождения CI.
