# To OpDB Headquarters — TASK-002 CORE / Verified Lens 0.1

**Date:** 2026-11-08.  **Status:** working disposable Python+SQLite engineering prototype, local tests passed. **OpDB is NOT an independent ready DBMS.**

## Executive result

Delivered the **first executable narrow KV version** of the Source→ChangeLog→Snapshot→Candidate→Full Proof→Bounded Tail Cutover→Immutable Lens→Version Guard→Source Fallback flow. The underlying durable Source is SQLite WAL + FULL, not new OpDB storage. `get` and bounded inclusive `scan` behave on bytes and sorted UTF-8 string keys. The candidate is fully compared to Source at a fixed revision before publication, with a small event tail replay under `BEGIN IMMEDIATE`.

Implemented components: `TruthStore` protocol, `SQLiteTruthStore`, `ChangeLog`, `Snapshot`, `Lens`, `VersionManager`, `VerifiedKV.cutover`, `VerifiedKV.fallback`, read-time version check and metrics. Background build API returns a Future and **never auto-activates**.

Tests: **29 automatic methods passed** (Python 3.13.5, SQLite 3.46.1, Linux). 750-step deterministic randomized state machine; external SQLite writers via another connection and subprocess, including a primary-key rename; rollback and two-key atomic reads; restart after hard process exit before/after commit; bad candidate, bad digest, skipped journal revision; schema drift; cutover failure before/after commit; memory and catchup cap failures; SQLite `integrity_check`.

## Observed smoke measurement (not a claim of improvement)

`python3 -m scripts.bench --rows 400 --ops 300 --seed 101 --output bench_result.json` generated a local JSON with source and lens per-call p50/p95/p99/max and total, plus build/full proof/cutover wall time, process CPU, estimated Lens Python bytes, max process RSS, SQLite database and WAL bytes, and total journal revisions. The source and accelerated reads were checked against the same generated byte values and `integrity_check=ok`.

The benchmark ran **one non-randomized sequential source-then-Lens sequence** on a warm file cache, without independently repeated seeds or CPU pinning. Any apparent advantage is unsubstantiated; the Lens is built on top of the SQLite primary-key index, and the true development cost must include trigger maintenance, full proof, memory and journal growth. The proof is not a power-loss or SSD benchmark.

## Safety contract status

| Invariant / requirement | Current status | Caveat |
|---|---|---|
| Source owns durable COMMIT | Delegated to SQLite | No own WAL/storage; hardware durability unproven |
| Every ordinary DML increments event log atomically | Implemented via SQLite AFTER triggers | DDL/trigger tampering privileged and unsupported |
| Consistent snapshot | Implemented via WAL read txn | Long snapshots can delay WAL checkpoint |
| Full verification before publication | Implemented and tested | O(N) pre-cutover proof; same implementation family, not formally independent |
| Bounded tail replay under writer lock | Implemented *event-count* cap | No firm time deadline or throughput guarantee |
| Atomic Lens publication | Implemented per-process pointer | Not cross-process or durable publication |
| Safe version mismatch fallback | Implemented on same SQLite read snapshot | No guarantee if metadata/triggers are maliciously changed |
| Cost guard/autonomous optimization | Disabled | R14 did not justify automatic acceleration |
| Formal ACID / linearizability of future OpDB | **Not proven** | SQL transactions are SQLite's, not native OpDB's |
| Production readiness | **REJECTED** | Proof Gate/Safety review outstanding |

## Priority engineering queue (proposed, not automatically authorized)

**P0 — correctness and Safety:** reconcile exact ADR-001 and TASK-001 Proof Gate contract; adversarial history/linearizability checker for real concurrent returns; stronger signature/privilege schema integrity; prove trigger+revision continuity across all supported multi-process writes; repeat crash injection at fsync/VFS boundary; ensure formal fallback if journal or meta cannot be trusted.

**P1 — resource and operations:** bounded journal GC with low watermark of all building candidates; WAL checkpoint starvation; memory/CPU/SSD/I/O budgets based on *process* and filesystem, not array estimates; precise cutover time budget without degrading writer p99; prevent writer starvation; safe shutdown and multiple OpDB readers across processes; schema migration protocol.

**P2 — native Rust port:** prototype same typed API with ownership-enforced immutable Lens generations, SQLite binding, structured error policy and exact test-equivalent corpus. Keep all semantic tests passing before introducing independent storage or index selection. C++ remains an alternative only with equivalent sanitizer/ownership controls.

**P3 — honest benchmarks:** repeat paired randomized A/B/A/B across seeds, 1k→1m keys, mixed external writers, cold/warm SSD effects, index-only SQLite comparisons, p99 and worst pause, complete cost of construction/proof/changelog and peak RAM; accept Lens only if advantage survives overhead and Safety gate.

## Blocking gaps for Headquarters to track

R7–R14 artifacts in the project library are heterogeneous: reports R12–R14 and several earlier research summaries are accessible, but archived source packages were not exhaustively audited or executed in this task.
