# ADR-001: OpDB Foundry architecture contract v0.1

- Date: 2026-11-08
- Status: Accepted project direction (implementation remains unverified)
- Project: OpDB (formerly MELDB)
- First milestone: Verified Lens 0.1

## Decision
OpDB aims to become a free, open, performant and reliable adaptive DBMS. Its first milestone is a research prototype that uses SQLite as the durable authoritative transactional source and tests optional derived data structures.

Correctness takes priority over performance. Derived indexes, caches, forecasts and materialized representations must never become the only source of committed truth. Unproven optimizations must be disabled or rejected when their estimated benefit is non-positive or their safety cannot be established.

Every performance claim includes full construction, migration and verification costs, CPU, RAM, I/O, tail latency, repeatable data and the reference implementation. Negative results and failed approaches remain part of the permanent record.

## Required properties to investigate
1. A confirmed transaction cannot be lost because an accelerator is changed.
2. A derived structure may be used only when its snapshot/version and complete change history have been verified.
3. The publishing point for a new structure must have well-defined concurrency semantics.
4. If validation cannot be completed, reading must fall back to a safe authoritative path.
5. Unexpected external writers must be prevented, tracked, or invalidate affected derived structures.
6. Failures of background work must not change committed source records.
7. Optimization controllers must not alter isolation or durability semantics.

These are REQUIREMENTS, **not proved guarantees** of the current prototype.

## Workstreams
Headquarters coordinates decisions. Safety specifies invariants and state changes (TASK-001 / proposed ADR-002). Core proposes typed APIs and implements prototypes (TASK-002 / proposed ADR-003). Quality verifies independently (TASK-003 / proposed ADR-004). Intelligence and Science are research streams until separately admitted to the integration process.

## Explicit exclusions
No claim of a complete SQL engine, independent crash-safe WAL, distributed transactions, production readiness or broad speed superiority. No production data, running servers or external projects may be altered by research tasks.

## Evidence gate
Every change requires reproducible commands, independent reference checks, environmental data, negative outcomes, and a documented Quality verdict. A passing finite test set is not a formal proof.
